在聊天界面里，我们输入一段话，很快就看到模型给出一段回答。这个过程看起来像一次完整的问答，模型内部却更像是在反复回答一个很小的问题：**接下来最可能出现的 token 是什么？**

## 从文本到 token

模型通常不会直接处理完整的汉字或单词，而是先由 tokenizer 把文本切成 token。一个 token 可能是一个字、一个词的一部分，也可能是标点或空格。输入消息、系统指令和对话历史都会被编码成 token 序列。

因此，字符数并不等于 token 数。不同语言、代码和特殊符号的切分方式也不同。上下文窗口和推理成本通常按 token 计算，估算长文长度时最好使用目标模型对应的 tokenizer。

## 上下文如何变成预测

每个 token 会映射为向量，经过多层 Transformer 计算。自注意力机制让当前位置能够结合前文信息形成新的表示；模型再根据当前序列计算词表中各个候选 token 的分数。

这些分数经归一化后可以看成下一个 token 的概率分布。模型根据解码策略选出一个 token，把它接到序列末尾，再重复计算。生成过程会在达到停止标记、长度上限或其他停止条件时结束。

```text
输入文本 → token 序列 → Transformer 计算
         → 下一个 token 的概率分布 → 选出 token → 重复
```

## 为什么同一个问题会有不同回答

如果总是选概率最高的 token，输出往往比较稳定，但也可能显得刻板。温度、top-p 等采样参数会改变候选分布的形状或范围，让生成结果在稳定性与多样性之间取舍。它们不会给模型增加新知识，也不能替代事实核查。

模型还受到上下文内容、训练数据、微调方式和系统指令的共同影响。更长的输入不必然带来更好的回答：无关内容会占据上下文预算，也可能让关键条件更难被利用。

## 一个实用的理解方式

可以把语言模型看成一个根据已有序列持续续写的系统。它能学到丰富的语言和模式，因此续写常常很有帮助；但概率高不等于事实正确。涉及数字、时效信息或高风险判断时，应通过可靠来源、工具调用或人工复核补上验证环节。
